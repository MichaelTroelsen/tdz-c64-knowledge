## Figure OCR - 2026-07-31

- ~~**Rasterize pages instead of (only) extracting embedded images**~~ — **DONE** (2026-07-31). `extract_document_figures` found figures only via `page.get_images(full=True)` (embedded raster XObjects), so vector-drawn schematics, memory maps and timing diagrams produced nothing. `TDZ_FIGURE_RASTERIZE_PAGES=1` now also renders each page's drawing regions via `page.cluster_drawings()` at `TDZ_FIGURE_RASTER_DPI` (200) and OCRs those (`server.py`, `_extract_vector_figures`). Deliberately **not** a full-page render — that would OCR the body text a second time on top of what the PDF's text layer already indexed. Clusters over `TDZ_FIGURE_RASTER_MAX_AREA` (0.9) of the page are borders and are skipped; clusters that sit on top of an already-extracted embedded image are skipped via `page.get_image_rects()` overlap. Rows now carry `source` (`embedded`/`vector`); existing databases get the column by `ALTER TABLE`. Verified against the live corpus: `Schematic_U36_adapter.pdf` has 0 embedded images and 1 vector cluster (the whole schematic), `goat_tracker_commands.pdf` 0 embedded and 11 clusters. Off by default — it is much more expensive per page.

- ~~**Parallelise the figure-OCR batch**~~ — **DONE** (2026-07-31). `extract_document_figures` now runs in two passes: all PyMuPDF work stays on the calling thread (PyMuPDF objects are not thread-safe) and only writes PNGs, then the OCR pass runs through a `ThreadPoolExecutor` of `TDZ_FIGURE_OCR_WORKERS` (default 1, i.e. previous behaviour). Covered by `test_ocr_workers_run_concurrently` (asserts calls actually overlap) and `test_parallel_and_serial_extraction_agree`. Note this parallelises *within* a document; the extraction worker itself is still one thread processing one job at a time, which is fine now that the expensive part is pooled.

- **Re-point or re-ingest the 131 PDFs whose source file is gone** - Of the 168 PDFs in the live KB, **131 no longer exist at their recorded `documents.filepath`** (121 under `tdz-c64-knowledge\uploads\`, 8 under `.tdz-c64-knowledge\temp\`, 2 under `downloads\`). Figure OCR skips them with `source file is no longer on disk`, and so would any future re-chunk, re-OCR or page-image feature — the indexed text is all that survives. **This also means the 2026-07-31 figure-OCR batch could only ever reach 37 documents, not 168.** **Files:** `server.py` (`extract_document_figures` already reports the condition; nothing else checks it). **Solution:** (a) a `health_check` metric counting documents whose `filepath` is missing, so this surfaces instead of being discovered by accident; (b) a way to re-point a document at a relocated file without reingesting; (c) decide whether `uploads/` should be treated as permanent storage rather than a staging area, since ingest records a path into it.

- **`figure_ocr_status` overstates what is reachable** - `documents_remaining` counts every unprocessed PDF, including the 131 whose source file is gone, so coverage can never reach 100% and the number invites a re-run that cannot do anything. **Solution:** split the count into reachable/unreachable using an `os.path.exists` check on `documents.filepath`.

- **Build a SID-archive ingestion path for HVSC / DeepSID** - Needed before the SID-music expansion can actually reach these two sources. **Problem:** There is no `.sid`/`.psid`/`.rsid` file parser and no `.zip`/`.lha` archive handling anywhere in the ingestion pipeline, so HVSC (a `.sid` file archive) can't be ingested at all. DeepSID is a JS single-page app driving a JSON API rather than static HTML, so the existing markdown-based scraper would only capture navigation chrome, not music metadata. **Files:** `server.py` (`_extract_text_for_file` dispatch - no `.sid`/`.zip` branch exists). **Solution:** At minimum, add a PSID/RSID header parser that turns a `.sid` file's metadata (title, author, released, chip model) into an ingestible text card; archive support (`.zip`/`.lha`) would let that run directly against HVSC's own distribution format. DeepSID likely needs its JSON API queried directly rather than scraped as HTML.
