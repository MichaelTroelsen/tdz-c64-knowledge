## Figure OCR - 2026-07-31

- ~~**Rasterize pages instead of (only) extracting embedded images**~~ — **DONE** (2026-07-31). `extract_document_figures` found figures only via `page.get_images(full=True)` (embedded raster XObjects), so vector-drawn schematics, memory maps and timing diagrams produced nothing. `TDZ_FIGURE_RASTERIZE_PAGES=1` now also renders each page's drawing regions via `page.cluster_drawings()` at `TDZ_FIGURE_RASTER_DPI` (200) and OCRs those (`server.py`, `_extract_vector_figures`). Deliberately **not** a full-page render — that would OCR the body text a second time on top of what the PDF's text layer already indexed. Clusters over `TDZ_FIGURE_RASTER_MAX_AREA` (0.9) of the page are borders and are skipped; clusters that sit on top of an already-extracted embedded image are skipped via `page.get_image_rects()` overlap. Rows now carry `source` (`embedded`/`vector`); existing databases get the column by `ALTER TABLE`. Verified against the live corpus: `Schematic_U36_adapter.pdf` has 0 embedded images and 1 vector cluster (the whole schematic), `goat_tracker_commands.pdf` 0 embedded and 11 clusters. Off by default — it is much more expensive per page.

- ~~**Parallelise the figure-OCR batch**~~ — **DONE** (2026-07-31). `extract_document_figures` now runs in two passes: all PyMuPDF work stays on the calling thread (PyMuPDF objects are not thread-safe) and only writes PNGs, then the OCR pass runs through a `ThreadPoolExecutor` of `TDZ_FIGURE_OCR_WORKERS` (default 1, i.e. previous behaviour). Covered by `test_ocr_workers_run_concurrently` (asserts calls actually overlap) and `test_parallel_and_serial_extraction_agree`. Note this parallelises *within* a document; the extraction worker itself is still one thread processing one job at a time, which is fine now that the expensive part is pooled.
