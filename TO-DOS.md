## Cross-Format Deduplication Defect - 2026-08-22

- **`.txt` and `.pdf` ingestion of identical content can never dedupe (pdf-page-break-markers-defeat-content-dedup)** - This is a distinct defect from the lost-source-files bullet above (that one is about missing *files*; this one is about a hashing defect that breaks *identity* across formats even when every file is present and healthy). **Mechanism:** `_generate_doc_id` (`kb/core.py:2184-2205`) generates the doc_id as an MD5 of the lowercased, whitespace-collapsed **first 10,000 words** of extracted text. `_extract_pdf_text` (`kb/ingest/_extraction.py:149-206`) joins each page's extracted text with the literal string `"\n\n--- PAGE BREAK ---\n\n"` (the join itself at line 206, with a second call site building the same joined string at line 90) **before** that hash ever runs - so a PDF and a `.txt` file holding the exact same content produce different doc_ids purely from marker words the extractor injects, not from any real content difference. **Measured evidence** (already recorded in the c=hacking availability-check bullet above, cited here rather than re-derived): on a real 19-page document, the PDF's pypdf-extracted text WITHOUT the PAGE BREAK join hashes to `cea9b4004347` - an EXACT match to the doc_id the live DB records for the already-indexed `.txt` version of the same document. WITH the join present (i.e. what `_extract_pdf_text` actually returns and what the live doc_id was computed from), it hashes to `f1aa9fc2b7da` instead. So on the PDF ingestion path, the entire miss is the extractor's own 72 injected marker words (18 page boundaries x 4 words each) - not OCR noise, not a real content difference. **Blast radius beyond the 21 c=hacking issues:** any document that exists in this corpus in one format and later gets re-ingested from another format - a re-scanned PDF of a document currently indexed as `.txt`, a vendor's PDF release of a document currently held as markdown - will silently fail to dedupe. `add_document`'s duplicate-content short-circuit (`kb/ingest/_documents.py:502-510`) compares against `doc_id in self.documents` and never fires, because the two formats' doc_ids never match in the first place; the result is a second, unlinked document created for content already in the KB, not an update to the existing record. **Why this is not fixed here:** changing what `_generate_doc_id` hashes (e.g. stripping PAGE BREAK markers, or any other normalization, before hashing) changes the doc_id computed for every future re-ingest of an already-indexed PDF, with no migration path for the ids already stored in the live DB - the same class of shared-hashing-function change this repo's own hazards already warn against making silently. That is a decision for a human to make deliberately (and to plan a migration for), not something to patch quietly inside a documentation task. **Files (read-only reference, not touched by this bullet):** `kb/core.py:2184-2205`, `kb/ingest/_extraction.py:90,149-206`, `kb/ingest/_documents.py:502-510`.

## markitdown as a fallback extractor - 2026-08-30

Rationale and scope for the five bullets below. `markitdown` (MIT, PyPI, v0.1.7,
Python 3.10+) converts DOCX/PPTX/EPUB/CSV/JSON/XML/MSG to Markdown. The fork at
`github.com/MichaelTroelsen/markitdown` is an **unmodified** mirror of
`microsoft/markitdown` - every recent commit on it is upstream (afourney,
danfiedler-msft, latest 2026-08-19) and the README documents no divergence - so
depend on the PyPI package, never the fork URL.

**It is a fallback only, never a replacement for an existing handler.** Its PDF
converter returns one flat markdown string with no page boundaries and no OCR,
which would break `_extract_page_references`, figure extraction and the PDF
viewer, all of which depend on `_extract_pdf_text` returning
`(text, total_pages, pdf_metadata)`. `.zip` likewise stays on the HVSC SID path
(`_extract_sid_archive`), and `.xlsx`/`.html`/`.txt` stay native. The fallback
fires only for extensions the current dispatch does not handle at all.

- **Add the `MARKITDOWN_SUPPORT` flag and keep it off the startup path (markitdown-feature-flag)** - `features.py` detects optional deps with `importlib.util.find_spec` (`_module_available`, line 72; see `FIGURE_SUPPORT` at line 169) precisely so the 30s MCP handshake budget is not spent on imports. markitdown must follow that pattern: `MARKITDOWN_SUPPORT = _module_available('markitdown')`, with `import markitdown` happening inside the extractor method, not at module level. **This matters more than for the other optional deps**: `markitdown/_markitdown.py` does `import magika` at module scope and `self._magika = magika.Magika()` in `MarkItDown.__init__`, so both the import *and* the construction pull in ONNX Runtime. Cache one `MarkItDown` instance on the `KnowledgeBase` rather than constructing per document. Add `markitdown`, `magika` and `onnxruntime` to `FORBIDDEN_AT_STARTUP` in `test_mcp_startup.py` (used by `test_heavy_modules_not_imported_at_startup`, line 212) so a future module-level import is caught. Add an optional extra to `pyproject.toml`: `markitdown[docx,pptx]>=0.1.7` - narrow extras only, never `[all]`, which drags in pandas, azure-*, pydub and SpeechRecognition.
